## Суть проекта

Лендинг для **нового продукта Марины Баяндиной**. Фундамент тот же, что в «Алхимии молодости: 7 ступеней» — антивозрастная и превентивная медицина, нутрициология. Но продукт другой: он **не решает здоровье целиком**, он решает **красоту** и только её — **кожа, волосы, ногти**. И решает **практически**: не «понять систему», а «сделать в понедельник».

Проще всего объяснить так: ступень 07 «Сияние» из «Алхимии молодости» здесь развёрнута в самостоятельный курс.

## Позиционирование и тон

Ключевое противопоставление, из которого растёт весь копирайтинг:

> Красота — это **биология**, а не баночка.

Против чего играем (это боль аудитории, её можно называть прямо):
- полка из 25 средств, которые не работают;
- витамины «на глаз», потому что подруга посоветовала;
- процедуры, выбранные по рекламе, а не по показаниям;
- советы уровня «пейте больше воды» и «нужно принять себя».

Что обещаем взамен: **причина вместо следствия** и **конкретное действие после каждого блока**.

Тон — как во всей линейке: живой русский, без канцелярита. Premium ≠ казённо.

## Аудитория

Женщины, ядро — 35–55 ⚠️ *(уточнить)*. Платёжеспособные, ухаживающие за собой осознанно. Уже тратят на косметологию и уход — и не понимают, что из этого работает. Пересекается с аудиторией «Алхимии молодости», но порог входа ниже: сюда приходят за конкретным результатом, а не за системой.

## Программа — методология Марины (2026-08-11)

**Утверждённый каркас:** 3 части — Кожа · Волосы · Ногти. Лекции **по 30 минут**, по 5–7 в части (в Ногтях меньше), плюс **материалы** и **бонусы** (состав ⚠️ не известен). Сейчас в сборке 15 лекций.

**Часть 1 · Кожа — утверждена дословно, 6 лекций:**
1. Строение и физиология кожи
2. Типы и механизмы старения
3. Аюрведические средства для молодости кожи (внутренние и наружные)
4. БАДы и нутрицевтики, включая обзор коллагена
5. Аппаратная косметология по типу кожи и старения — *приглашённый спикер*
6. Инъекционная косметология — *приглашённый спикер*

**Часть 2 · Волосы — от Марины только «примерно также»** ⚠️. В контенте лежит моя параллельная раскладка на 6 лекций (строение; типы выпадения; аюрведа; БАДы; современная трихология — приглашённый спикер; уход/окрашивание/седина) с `draft: true` — на сайте помечена как ждущая утверждения.

**Часть 3 · Ногти — утверждена, 3 лекции:** строение и функции; добавки для крепких ногтей (аюрведа + современная нутрициология); ванночки.

Старый черновик «7 блоков» (База, Гормоны, Уход, Процедуры…) этой методологией **отменён**.

## Деплой

**Один исходник — четыре сайта.** Вся вёрстка и весь контент живут в `razovik-hub/krasota` (папка `~/Documents/Krasota`). Оттуда собираются:

- **хаб** `razovik-hub/krasota` → `/krasota/` — страница выбора, деплоится сама через GitHub Actions на push в `main`;
- **три сайта вариантов** → `/krasota-a/`, `/krasota-b/`, `/krasota-c/` — собираются скриптом и выкладываются в отдельные репозитории готовой статикой.

```bash
npm run publish:variants   # собрать три сайта и выложить их
```

Как это устроено (`scripts/build-variants.mjs`): для каждого варианта скрипт временно подменяет `src/pages/index.astro` на страницу этого варианта, собирает с `BASE_NAME=krasota-<id>`, выкидывает из результата страницы-дубли и кладёт `.nojekyll` (без него Pages выбрасывает каталог `_astro` — он начинается с подчёркивания). Затем пушит готовый `out/<id>` в свой репозиторий force-пушем. Исходный `index.astro` возвращается на место в любом случае, даже если сборка упала.

Почему так, а не три копии проекта: **контент правится в одном месте**. Меняем текст в `src/content/*.md` → `npm run publish:variants` → изменение разъезжается по всем трём сайтам.

Старые адреса `/krasota/a/`, `/krasota/b/`, `/krasota/c/` оставлены рабочими, чтобы ранее отправленные ссылки не отвалились.

⚠️ Имена репозиториев рабочие. Когда будет название продукта — победивший вариант переезжает в репозиторий с нормальным именем, остальные удаляются вместе с хабом.

### Зеркала на Vercel

Те же три варианта живут и на Vercel (CLI залогинен как `razovik-hub`, команда «razovik-hub's projects»): `krasota-a.vercel.app`, `krasota-b.vercel.app`, `krasota-c.vercel.app`. Флаг `--vercel` у `build-variants.mjs` собирает лёгкие версии в `out/vercel-{id}` (base=/, фото абсолютными ссылками с GH-хаба), деплой — `vercel deploy --prod --yes` из каталога сборки.

### Заявки → Telegram

Форма (`src/components/LeadForm.astro`) на всех шести адресах шлёт POST в одну Vercel-функцию: проект **krasota-api**, эндпоинт `https://krasota-api.vercel.app/api/lead` (исходник `api/lead.mjs`, адрес вшивается в сборки константой `LEAD_API` в `build-variants.mjs`). Функция пересылает заявку в Telegram через Bot API; нужны env `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` в настройках проекта на Vercel — пока их нет, отвечает 503.
